# §0. 요약 — 소급 불가능한 2개의 의존성

조사 전체에서 **지금 결정하지 않으면 연구 자체가 성립하지 않는** 항목은 정확히 두 개다. 나머지는 나중에 보완할 수 있다.

| # | 요구사항 | 왜 소급 불가능한가 | 없으면 죽는 것 |
|---|---|---|---|
| **P-1** | **다계층 전해상도(full-resolution) 참조 코퍼스 아카이빙을 도입 시점부터 시작** | 이미 rollup된 데이터로는 "downsampling이 무엇을 파괴하는가"를 연구할 수 없다. 5분 평균에서 1초 신호를 복원할 방법은 없다 | `09` §4.3 / §12의 **retention 해상도 축** — 전역적으로 생존한 유일한 novelty. 즉 최우선 후보 C1 전체 |
| **P-2** | **Slurm 노드 상태 이력에 `actor` 필드(누가/무엇이 이 상태 변화를 일으켰는가) 기록** | 과거 drain 기록에 "사람이 했는가 자동화가 했는가"를 사후에 붙일 방법이 없다. 로그 상관으로 일부 추정은 되나 behavior policy를 재구성할 수는 없다 | 후보 C6(remediation off-policy 평가) **전체**. `09` §11 C6 판정이 명시적으로 조건부 `DROP`이다 |

**두 항목 모두 소프트웨어 개발이 아니라 운영 정책 결정이다.** P-1은 저장 예산 배정, P-2는 상태 변경 경로에 필드 하나 추가.

**차선책도 명시한다:** P-1의 전면 시행이 예산상 불가능하면 §4.3의 **계층적 참조 코퍼스**(전 노드 저해상도 + 회전 표본 노드군 전해상도 + 인시던트 주변 전해상도 pin)로 축소 가능하며, 이것으로도 C1의 핵심 실험(Q-δ)은 성립한다. P-2는 대안이 없다.

# §1. 원칙 — 무엇이 소급 복구 불가능한가

연구용 데이터 요구사항을 판단하는 기준. 운영 요구사항과 다르다.

| 등급 | 정의 | 예 | 정책 함의 |
|---|---|---|---|
| **N (Non-recoverable)** | 수집 시점에 남기지 않으면 영구 소실 | 1초 해상도 원신호, 상태 변경의 actor, 조치 시점의 후보 대안 집합, 수집기 오버헤드 실측 | **지금 결정** |
| **R (Reconstructable)** | 원본이 남아 있으면 나중에 파생 가능 | rollup 시계열, 파생 지표, feature vector, 임베딩 | 나중에 |
| **A (Administrative)** | 사람의 승인/행정 절차로 나중에 확보 가능 | 티켓 export, RMA 기록, 운영자 판정 label | 나중에, 단 **접근 경로는 지금 확인** |
| **X (Excluded)** | 개인정보·보안 사유로 남기지 않는다 | §5 | **지금 금지 규칙 확정** |

**흔한 오판 3가지:**
1. *"압축해서 오래 보관하면 된다"* — 손실 압축은 오차 bound를 보장하지만 **시간 해상도를 보존하지 않는다**. `09` §4.3의 near-miss 표에서 Z-checker·SZ/ZFP 계열을 반례로 거부한 이유와 같다. lossless 압축은 유효하다.
2. *"필요하면 그때 수집을 늘리면 된다"* — 연구 대상이 **과거 인시던트**다. 인시던트는 재현되지 않는다.
3. *"운영에 필요 없으니 안 남긴다"* — P-1/P-2는 정확히 **운영에는 즉시 필요 없지만 연구에는 필수인** 항목이다. 운영 요구사항만으로 설계하면 반드시 빠진다.

## 2.1 축 C1 — Telemetry policy 최적화 (최우선 후보, `09` §12)

**연구 근거:** π = {(m_i, f_i, r_i(τ))}에 대한 cost–quality Pareto frontier. 특히 Q-δ(downsampling이 파괴하는 temporal ordering / lag 정보).

### (a) 전해상도 참조 코퍼스 — **등급 N, P-1의 실체**

| 계층 | 최소 해상도 | 필수 필드 | 비고 |

|---|---|---|

### (c) 교란 측정 실험 창 — **등급 N, 도입기에만 가능**

`09` §4.5: GPU/Redfish/Slingshot 세대에서 rate별 애플리케이션 교란 측정은 **생존한 gap**이다. 그러나 이것은 데이터가 아니라 **실험 시간**을 요구하고, production 진입 후에는 전용 실험 창을 얻기가 극히 어렵다.

**도입/수락시험(acceptance) 기간에 반드시 확보할 것:**
- 고정 벤치마크 집합(HPL, HPCG, 대표 사용자 앱 2–3종, GPU 집약 1종, I/O 집약 1종, 통신 집약 1종)
- 각 벤치마크 × **수집 rate 최소 5수준**(예: off / 5 s / 1 s / 200 ms / 100 ms) × 규모 최소 3수준(단일 노드 / 중간 / 최대 가능) × 반복 최소 5회
- 각 실행의 **런타임, 에너지, 통신 시간 분해**를 원본으로 저장
- 동시에 수집기 cgroup 사용량 기록

**이것이 DCDB SC'19(`09` §4.2)의 GPU 세대 대응물이며, 논문의 비용 축 근거 전체다.** 수락시험 계획서에 항목으로 넣지 않으면 사라진다.

### (d) 등급 R (지금 만들 필요 없음)

rollup 시계열, feature vector, 임베딩, 정규화된 파생지표, Pareto frontier 자체 — 모두 (a)가 있으면 사후 생성 가능. **지금 이것만 남기고 원본을 버리면 안 된다는 점만 지킬 것.**

### (e) 없으면 죽는 주장

- 전해상도 코퍼스 없음 → **Q-δ 불가 → C1 전체 소멸**(대체 축이 없다. `09` §4.6에서 5개 하위주장 중 무조건 생존한 것은 retention 하나뿐)
- 비용 실측 없음 → cost 축이 추정치가 되어 desk reject 위험
- 교란 실험 창 없음 → C_perturb 항 소멸 → AWStream과의 차별점 (ii) 소멸(`09` §4.4)

## 2.2 축 A/C5 — Cross-layer RCA & fail-slow 판별

**연구 근거:** `09` §5.5 — 잔존 gap은 **conjunction으로만 성립**한다(계층 수 × 원인 클래스 × 운영자 확인 label × 배치 정보). 따라서 join 가능성이 데이터 요구사항의 전부다.

### (a) Join key — **등급 N, 최우선**

계층별 telemetry가 사후에 결합되지 않으면 cross-layer RCA는 존재하지 않는다. **모든 계층의 모든 레코드에 다음이 있어야 한다:**

| Join 축 | 필수 필드 | 흔한 실패 모드 |
|---|---|---|
| **시간** | UTC, **단조 증가 보장**, 소스별 clock offset 기록, NTP/PTP 동기 상태 | ⚠️ **cascade lag 연구는 계층 간 clock skew에 직접 영향받는다.** 시설 BMS와 노드 OS의 시계가 수 초 어긋나면 Q-δ의 lag 측정이 무의미해진다. **소스별 offset을 시계열로 남길 것** |
| **노드** | 표준 노드 ID + **물리 위치**(랙/섀시/블레이드/슬롯) + **전원 계통** + **냉각 계통(CDU/루프)** + **fabric 위치**(스위치/포트/그룹) | 물리 토폴로지 매핑을 시계열로 남길 것 — 유지보수로 바뀐다. **한 시점 스냅샷만 있으면 과거 인시던트의 이웃 관계를 재구성할 수 없다** |
| **Job** | Slurm job/step ID가 **모든** 계층에 전파(Lustre jobstats, GPU 프로세스 귀속, fabric 흐름 귀속 가능한 범위) | job↔자원 귀속이 없으면 cross-job 간섭 원인 클래스가 붕괴 |
| **Fabric** | 노드↔포트↔스위치↔그룹 매핑 + **라우팅/토폴로지 변경 이력** | 재라우팅 이벤트가 없으면 혼잡 원인 귀속 불가 |
| **저장** | 노드↔OST/MDT 매핑, OST↔서버↔풀 매핑, 변경 이력 | |

### (b) Job 배치 이력 — **등급 N**

`09` §5.4: *scheduler placement as causal variable*는 **좁혀서 생존**한 축이다. 이것은 다음을 요구한다:

- 모든 job의 **실제 할당 노드 리스트**(요약 아님, 전체 리스트)
- 할당 시점의 **노드 상태 스냅샷**(어떤 노드가 drain/down이었는가)
- **동시 실행 job 집합** 재구성 가능성 — 즉 시작/종료 시각이 초 단위로
- 요청 자원 vs 실제 할당(파티션, QoS, 제약, gres)
- backfill 여부, 큐 대기 시간, 우선순위 구성요소
- **선택되지 않은 대안**: 스케줄러가 고려했던 후보 노드 집합 — **등급 N이고 대부분의 사이트가 남기지 않는다.** Slurm은 기본적으로 이것을 기록하지 않는다. 확보 가능하면 placement counterfactual 연구가 열린다

### (c) 운영자 확인 label — **등급 A(행정), 그러나 지금 경로를 열어야 함**

`09` §11 C5: *"운영자 확인 label이 몇 건인가? Kaleidoscope 843, ClusterRCA 739가 기준이다."* — 이것이 SC 심사의 사실상 진입 장벽이다.

지금 확보해야 하는 것은 데이터가 아니라 **프로세스**:
- 인시던트마다 **구조화된 사후 판정 필드**를 채우는 운영 절차(자유 텍스트만으로는 label이 되지 않는다)
- 최소 필드: 인시던트 ID, 시작/종료 시각(추정과 확정 구분), 영향 노드 집합, **근본 원인 클래스**(사전 정의된 taxonomy), 확신도, 판정자, 판정 시각, 근거 telemetry 참조
- **원인 taxonomy를 지금 정의**할 것 — 사후에 통일하면 초기 기록이 매핑되지 않는다. 최소 클래스: 하드웨어 고장 / 열·전력 throttle / fabric 혼잡 / fabric 하드 오류 / 저장 경합 / 저장 고장 / cross-job 간섭 / 소프트웨어·설정 / 사용자 코드 / 미확정
- 티켓 시스템·RMA 기록의 **export 권한**을 지금 확인(`09` §11 C4의 feasibility 반론)

### (d) 없으면 죽는 주장

- clock offset 미기록 → lag 기반 RCA와 Q-δ 모두 신뢰 불가
- 물리/fabric 토폴로지 이력 없음 → 이웃 관계·cascade 경로 재구성 불가 → conjunction 붕괴
- 원인 taxonomy 사후 정의 → label 코퍼스 크기가 심사 기준 미달

## 2.3 축 F/C6 — Safe remediation & off-policy 평가

**연구 근거:** `09` §7.4 — 잔존 주장 3개(조치 클래스 확장 / 형식적 OPE / provenance·accountability). 세 개 모두 **behavior policy의 기록**을 요구한다.

### (a) `actor` 필드 — **등급 N, P-2**

**Slurm 노드 상태 변경 이력의 모든 레코드에 다음이 있어야 한다:**

| 필드 | 값 예시 | 왜 필요한가 |
|---|---|---|
| `actor_type` | `human` / `automation` / `health_check` / `prolog_epilog` / `scheduler` / `vendor_tool` / `unknown` | **behavior policy 재구성의 유일한 근거.** OPE는 "과거 정책이 이 상태에서 무엇을 했는가"를 알아야 한다 |
| `actor_id` | 계정/스크립트명/체크명 | 어떤 자동화 규칙이었는지 |
| `trigger` | 규칙 ID, 임계값, 발화 telemetry 참조 | 정책의 입력 상태 복원 |
| `reason_code` | 사전 정의 코드 (자유 텍스트와 **병기**) | 자유 텍스트만이면 label이 되지 않는다 |
| `prev_state` / `new_state` | drain/down/resume/... + 이유 | |
| `ts_decision` / `ts_effective` | 결정 시각과 실제 반영 시각 분리 | 지연이 비용이다 |
| `affected_jobs` | 그 시점 해당 노드의 job/step 목록 + 처리(kill/requeue/완주 대기) | blast radius의 실체 |
| **`alternatives_considered`** | 가능하면 | 없으면 counterfactual 공간이 비어 있다. 확보 시 강력 |
| `reverted` / `revert_ts` / `revert_actor` | | 오조치율(FRR) 추정의 유일한 근거 |

**이 중 `actor_type` 하나가 결정적이다.** `09` §11 C6: *"Slurm 노드 상태 이력에 actor 필드가 없으면 off-policy 평가가 불가능하다"* → 판정이 `SC-STRETCH (조건부)`이며, 없으면 `DROP`.

**구현:** Slurm 자체 스키마를 바꿀 필요는 없다. 상태 변경을 수행하는 **모든 경로**(운영자 CLI 래퍼, health check, prolog/epilog, 벤더 도구, 자동화 스크립트)를 감사 로그로 수렴시키면 된다. 핵심은 **경로를 우회한 직접 `scontrol` 호출을 남기지 않는 것** — 이것이 정책 결정이다.

### (b) 조치의 실제 비용 — **등급 N**

`09` §11 C6의 SC 상승 메커니즘: HPDC'24가 다루지 않는 **조치 클래스 확장**. 그것을 측정하려면:

- requeue된 job의 **큐 위치 손실**(requeue 전/후 예상 시작 시각) — 사후 계산 불가, 그 시점 큐 상태가 필요
- **fairshare charge-back** 이력(취소/재실행 시 과금 처리)
- **reservation 단편화**: 예약 생성/변경/취소 이력과 그로 인한 유휴 노드-시간
- drain된 노드의 **실제 유휴 시간**(drain→정비 시작→정비 완료→resume 각 시각)
- 정비 결과: 실제 결함 확인 여부(= 그 drain이 옳았는가)

### (c) 없으면 죽는 주장

- `actor_type` 없음 → **C6 전체 `DROP`**(`09` §11)
- revert 기록 없음 → FRR 추정 불가 → CMDP 제약의 경험적 근거 소멸
- 큐 상태 스냅샷 없음 → 조치 클래스 확장이 HPDC'24의 node-hour 모델로 환원되어 novelty 소멸

### 등급 N 항목

## 2.5 축 D/C4 — Label semantics

**연구 근거:** `09` §11 C4 — 재프레이밍된 기여는 **"label이란 무엇인가"를 측정 문제로** 다루는 것. 이것은 **동일 사건에 대한 복수 소스의 독립적 기록**을 요구한다.

### 등급 N 항목

**핵심: 소스를 통합하지 말고 각각 원본으로 남길 것.** 통합하면 소스 간 불일치(κ)를 측정할 수 없고, 그 불일치가 바로 연구 대상이다.

| 소스 | 남겨야 하는 것 |
|---|---|

| health check | 각 체크의 개별 결과(통과/실패/오류)와 시각 — 요약 판정이 아니라 개별 |
| 티켓 | 생성/상태전이/해결 코드/연결된 노드·job (등급 A, 경로 확보) |

**추가 등급 N:** 계획 정비 일정(planned maintenance calendar). `09` §11 C4의 *"계획-비계획 confound 분리"*가 여기 걸려 있다. 사후에 "이 down이 계획된 것이었나"를 알 방법이 없다.

# §4. Retention 정책 설계 — 연구 축과 직결되는 부분

이 절이 이 문서의 핵심이다. `09` §4.3에서 **retention 해상도를 결정변수로 다룬 peer-reviewed 논문을 metrics store 영역에서 찾지 못했다**는 것이 전체 조사에서 무조건 생존한 유일한 novelty다. 그런데 그 연구를 하려면 **retention 정책을 사후에 실험할 수 있는 원본이 있어야 한다.** 즉 연구 대상과 연구 전제가 같은 데이터다.

## 4.1 흔한 운영 기본값이 연구를 죽이는 방식

전형적 TSDB 기본 정책:

| 나이 | 해상도 | 결과 |
|---|---|---|
| 0–7 d | 원본 | |
| 7–30 d | 1 min 평균 | |
| 30 d–1 y | 5 min 평균 | |
| > 1 y | 1 h 평균 또는 삭제 | |

**이 정책 하에서 8일 전 인시던트의 lag 구조는 이미 소실되어 있다.** cascade 순서(예: CDU 온도 상승 → GPU throttle → 통신 지연 → job 성능 저하)의 각 단계 간격이 수 초 규모라면 1분 평균에서 순서가 사라진다. Q-δ는 정확히 이 손실을 측정하려는 것인데, 데이터가 이미 손실된 상태로 저장된다.

**따라서 운영 rollup 정책과 별개로 연구용 원본 보존이 필요하다.** 두 개는 같은 저장소일 필요가 없다.

## 4.2 2계층 설계 — 운영 store와 연구 코퍼스 분리

| | 운영 store (TSDB) | 연구 코퍼스 (아카이브) |
|---|---|---|
| 목적 | 대시보드, 알람, 즉시 조회 | 소급 실험, 재현, 논문 |
| 해상도 | 운영 요구대로 rollup 허용 | **원본 그대로** |
| 형식 | Prometheus/VictoriaMetrics/DCDB 등 | **컬럼형 + lossless 압축**(Parquet + zstd 권장) |
| 접근 | 저지연 쿼리 | 배치 스캔. 저지연 불필요 |
| 매체 | SSD/NVMe | **HDD/객체 저장소/테이프 허용** |
| 보존 | 운영 정책 | 최소 12개월, 목표 시스템 수명 |
| 비용 특성 | 비쌈 | **원본 보존이 저렴해지는 지점** |

**중요:** 연구 코퍼스는 저지연 요구가 없으므로 **가장 싼 매체에 둘 수 있다.** "전해상도 다년 보존은 비용상 불가능"이라는 판단은 대개 운영 TSDB 등급 저장소를 가정한 것이다. 컬럼형 + zstd + 객체 저장소 조합에서 비용 추정을 다시 할 것.

**부수 효과:** 이 2계층 구조 자체가 §2.1(b)의 C_storage 데이터를 자연스럽게 생성한다. 그리고 **운영 store의 rollup 정책과 연구 코퍼스의 원본을 비교하는 것이 곧 Q-δ 실험의 실행 형태다**(§`11` 참조).

## 4.3 예산 제약 시의 계층적 참조 코퍼스 (차선책)

전 노드 전해상도 다년 보존이 불가능할 경우. **이 축소판으로도 C1의 핵심 실험은 성립한다.**

| 계층 | 범위 | 해상도 | 기간 |
|---|---|---|---|
| **T0 — 전수** | 전 노드, 전 계층 | 운영 rollup 허용 | 시스템 수명 |
| **T1 — 회전 표본** | 노드의 **5–10%**, 정기 회전(예: 월 단위로 대상 교체) | **전해상도 1 s** | 연속 |
| **T2 — 인시던트 pin** | 인시던트 전후 **±24 h**, 영향 노드 + **대조군 노드**(동일 랙/다른 랙/다른 CDU) | **전해상도** | 영구 |
| **T3 — 실험 창** | 교란 측정·주입 실험 기간 전체 | **전해상도 + 100 ms burst** | 영구 |

**T1의 회전이 중요한 이유:** 고정 표본이면 표본 노드에만 있는 특성(위치, 냉각 루프, fabric 그룹)이 결과를 편향시킨다. 회전하면 시스템 전체를 시간에 걸쳐 커버한다.

**T2의 자동화가 결정적:** 인시던트 발생 시 **자동으로 해당 구간을 rollup 대상에서 제외(pin)**하는 메커니즘이 필요하다. 사람이 기억해서 하면 반드시 놓친다. 알람 발화 시점에 pin 요청을 걸고, 사후 판정에서 확정/해제하는 구조.
→ 이것은 Hindsight(NSDI'23)의 *retroactive sampling* 아이디어의 metrics·retention판이며, `09` §4.3에서 Hindsight를 "발표된 최근접(단 trace이고 binary)"으로 분류한 이유다. **차별점은 binary keep/discard가 아니라 해상도라는 점** — 이것을 논문에서 명시적으로 positioning할 것.

**T2의 대조군이 결정적:** 영향 노드만 pin하면 "정상일 때는 어땠는가"가 없어서 어떤 통계 비교도 불가능하다. 반드시 동시각 대조군을 함께.

## 4.4 확인 필요 — retention 축 착수 전 falsification 점검

`09` §4.5의 미해결 위험이 이 축에 직접 걸린다. **데이터 보존은 지금 시작해도 되지만, 논문 착수 전에 다음을 확인할 것**(→ `12_UNRESOLVED_EVIDENCE_AND_WATCHLIST.md`):

1. **VLDB/SIGMOD/ICDE/EDBT/CIDR의 rollup·retention 스윕** — 미검색 최대 영역. Monarch/Gorilla/ByteSeries/TimeUnion/ModelarDB/Timon 계열이 하류 분석 품질을 평가했다면 축이 약화된다
2. **PIKA CLUSTER'20 PDF** — Taurus GPU 파티션에서 rate별 오버헤드를 보고했다면 §2.1(c)의 GPU 교란 gap이 죽는다
3. **Tuncer TPDS'19 PDF** — 민감도 연구가 window가 아니라 sampling interval을 변화시켰다면 약화
4. **Hindsight NSDI'23 전문** — retroactive retention의 정확한 범위

# §5. 저장하면 안 되는 것 — 개인정보 / 보안

> **이 절은 연구 편의보다 우선한다.** 아래 항목은 "익명화하면 된다"가 아니라 **애초에 수집·저장하지 않거나, 수집 지점에서 즉시 변환하는 것**을 원칙으로 한다.
> 실제 적용 시 KISTI 정보보호 및 개인정보보호 규정, 「개인정보 보호법」, 기관 IRB/보안심의 절차의 판단이 이 문서보다 우선한다. 이 절은 **연구 설계 단계에서 스스로 걸러야 할 목록**이지 법적 판단이 아니다.

## 5.3 원본 로그 보존과 스크러빙의 충돌 — 명시적 결정 필요

§2.1(a)는 *"system logs를 원본 그대로, 정규화 전"* 보존할 것을 요구한다. §5.1은 로그에 우발 유입되는 비밀정보·경로·개인정보를 저장하지 말 것을 요구한다. **이 둘은 직접 충돌한다.**

**권고 해법 — 3단 구조:**

| 단계 | 내용 | 접근 |
|---|---|---|
| **L-raw** | 스크러빙 전 원본. 파서 개선 시 재처리용 | **운영 보안 구역**. 연구자 직접 접근 불가. 보존 기간 단기(예 90 d) |
| **L-scrubbed** | 패턴 스크러빙(비밀정보·경로·이메일·주민번호 형식) + 가명화 적용. **라인 구조와 타임스탬프는 보존** | 연구 코퍼스. 장기 보존 |
| **L-public** | 공개 릴리스용. §5.4 추가 변환 | 외부 |

**스크러빙은 손실이며 되돌릴 수 없다.** 따라서 스크러빙 규칙 자체를 버전 관리하고, 각 라인에 어떤 규칙이 적용되었는지 표시할 것. 그렇지 않으면 "이 패턴이 없는 것이 실제 없는 것인지 지워진 것인지" 구별되지 않아 로그 분석 결과가 신뢰를 잃는다.

## 5.4 공개 데이터셋 릴리스 시 추가 요구 (해당 시)

`09` §8.3의 발견 — *"연구와 실무를 잇는 다리는 워크숍 논문이 아니라 데이터셋이다"*(M100 ExaData, MOSAIC, HPC-ODA 계열). 따라서 릴리스는 전략적으로 중요하지만 위험도 가장 높다.

- 노드 ID를 **재매핑**(물리 위치와의 대응 제거 또는 상대 위치만 유지) — 단 topology 연구용으로 상대 구조는 유지해야 한다. 이 균형이 릴리스 설계의 핵심
- 시간축 **오프셋 이동** 검토(절대 시각이 운영 사건과 결합되어 재식별 경로가 된다). 단 외기 조건·전력 요금 등 외부 데이터와의 결합 연구를 막는다 → 용도에 따라 결정
- 사용자·그룹 가명을 릴리스마다 **다른 키로** 생성(릴리스 간 연결 공격 방지)
- 극단값 처리: 단일 대형 job이 특정 사용자로 자동 특정되는 경우
- **기관 승인 절차를 지금 확인**할 것. `09` §11 C7의 feasibility 반론이 정확히 이 지점이다

## 5.5 정리 — 판단 규칙

> **"이 필드가 없어도 연구 질문에 답할 수 있는가?"** 답이 예이면 저장하지 않는다.
> **"이 필드가 유출되면 사용자나 기관에 회복 불가능한 피해가 있는가?"** 답이 예이면 수집 지점에서 변환한다.
> 두 질문 모두 애매하면 **저장하지 않고 진행하다가 필요할 때 승인 절차로 추가**한다 — 반대 순서(먼저 모으고 나중에 정리)는 되돌릴 수 없다.

**단, 이 보수성이 §0의 P-1/P-2에 적용되지 않도록 주의할 것.** P-1(전해상도 하드웨어·시스템 metric)과 P-2(actor 필드)는 **개인정보를 담지 않는다.** 노드 온도와 drain 사유 코드는 개인정보가 아니다. 개인정보 우려로 P-1/P-2를 축소하는 것은 범주 오류다.

| 구시스템 아카이브 보존 | C2의 cross-generation 쌍 | 공개 데이터셋 조합으로 부분 대체(단 §6.2의 CENTILE 반론에 더 취약해진다) |
| 이중 수집 | C10, 그리고 C1의 "무엇을 놓치고 있는가" 전제 | 없음(사후에 병렬 경로를 추가해도 과거 불일치는 모른다) |
| clock offset 기록 | Q-δ의 lag 측정 신뢰성 | 없음 |
| 토폴로지 이력 | cascade 경로 재구성 → conjunction 붕괴 | 없음 |

**한 문장 요약:** `09`의 falsification을 통과한 연구 축은 모두 **"지금 남기지 않으면 존재하지 않는 데이터"**에 의존한다. 문헌 조사로 확인한 것은 어떤 논문을 쓸 수 있는지가 아니라, **어떤 데이터를 남기지 않으면 어떤 논문도 쓸 수 없는지**였다.
