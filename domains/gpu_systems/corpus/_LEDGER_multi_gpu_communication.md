## Reading notes that govern every row

1. **`prior_corpus_check` for every row in this cluster is `KNOWN_EXTERNAL_CORPUS_NOT_IMPORTED`.** A repo-wide grep (exact title, normalized title, DOI, arXiv ID, first author + distinctive term) found **no existing corpus analysis** for any assigned paper — hits were confined to `domains/gpu_systems/census/*.md` rows, `census/_evidence/` program dumps, and raw TOC dumps under `domains/hpc_quantum/corpus/quantum-hpc-survey/working-evidence/` (existence evidence only). But `domains/ai_hpc_systems/` is `EXTERNAL_IMPORT_PENDING`: an ~80-paper AI/HPC corpus with GPU communication/collectives coverage is known to exist outside this repo and is **not imported**. Many papers in this cluster plausibly belong to it. **No claim of non-duplication is made for any row.** A central overlap registry must carry this flag.
2. **Control placement was never inferred from an abstract.** Per `governance/ANTI_HALLUCINATION_RULES.md`, GPU-initiated vs host-initiated distinctions require the paper or the code. Rows whose access state is `ABSTRACT_ONLY` or `CLOSED_ACCESS` carry `UNKNOWN` for control placement, without exception.
3. **Stable-ID band.** `GPU-ASPLOS24-21`, `GPU-SC26-21` and `GPU-SC26-22` sit in a high band because `-01`/`-02` in those venue-years were concurrently assigned by other clusters; per `governance/ID_NAMING_RULES.md` an ID is never reused, so these were renumbered rather than collided. Uncontested venue-years use `-01`/`-02` as specified.
4. **ACM/IEEE access.** `dl.acm.org` returns 403 and `ieeexplore.ieee.org` returns 418 from this environment, so several papers the census marks as having an open publisher PDF are nonetheless `CLOSED_ACCESS` *as determined here*. That is an access-path limitation, not a statement about the paper's licence.

## Control-placement vocabulary used in this ledger

| Term | Meaning |
|---|---|
| `host-driven` | CPU enqueues the operation; stream-ordered; host or host proxy thread posts to the NIC |
| `device-triggered` | Hardware (tracker, NIC counter + pre-staged work) initiates; neither host nor a kernel issues the operation |
| `device-resident` | A GPU kernel itself issues the put/get or posts the work-queue element |
| `UNKNOWN` | Not established from the paper or code — never guessed |

| Placement | Papers where it was **established** (paper and/or code, never abstract) |
|---|---|

| `device-resident` | `GPU-SC26-21` (NCCL device-side API over CUDA VMM symmetric memory + GDAKI); GICC **on InfiniBand** (kernel builds WQEs and rings the mlx5 UAR doorbell); MSCCL++ **MemoryChannel and SwitchChannel** (peer load/store; `multimem.red` PTX); aCG **device-initiated path** (`nvshmemx_double_put_signal_nbi_block` inside CG kernels) `[code]`; NIMBLE (paper-asserted, code-unverified) |
| `UNKNOWN` | all 32 rows read only at census/abstract/official-program depth, plus TCCL (framing unread) and GPUs All Grown-Up (communication placement not established) |

**The decisive observation**: control placement is not a property of a year or of a "generation" of the field — it is a property of the **fabric**. GICC and MSCCL++ both state, from opposite directions, that inter-node RDMA initiation depends on what the NIC exposes to a kernel: MSCCL++ says "current hardware interconnects require a CPU thread to initiate the data transfer" and does not support GPU-initiated RDMA; GICC shows that on mlx5 InfiniBand a kernel *can* post directly, while on Slingshot's CXI provider it cannot and must settle for triggering. Within an NVLink domain (`GPU-SC26-21`, MSCCL++ MemoryChannel/SwitchChannel) device-resident control is routine; across a scale-out fabric it is fabric-conditional.

## E. Is the progression "GPU-aware MPI → device-initiated communication → symmetric memory → GPU-resident collective control" supported by the papers' own related work?

**Answer: NOT SUPPORTED as a progression.** It is a real *taxonomy of mechanisms* but the
papers' own related-work sections and citations do not describe it as a sequence the field
has traversed. Four kinds of counter-evidence, all `[paper]`:

1. **The stages coexist in the same venue-years, and the newest papers are not the most
   device-resident.** IPDPS 2026 contains both NIMBLE (device-resident data path asserted)
   and PCCL / *The Big Send-off* (fully host-initiated MPI + vendor libraries at 2,048
   GPUs). SC 2026 contains both *Every Microsecond Matters* (device-resident via GDAKI)
   and NCCLZ (host-enqueued `ncclAllReduce`, preserved deliberately). If this were a
   progression, the 2026 host-driven papers would be rearguard work; they are not — PCCL
   reports up to 168× over RCCL for reduce-scatter at 2,048 MI250X GCDs on Frontier.

2. **The symmetric-memory "stage" is actively contested, not passed through.** MSCCL++
   (ASPLOS 2026) states: "We could not find any implementation where NVSHMEM outperforms
   NCCL (or MSCCL++) for collective communication" — an explicit rejection. T3 (ASPLOS
   2024) argues NVSHMEM "requires explicit synchronization and doesn't automatically
   orchestrate collective progress". *Every Microsecond Matters* (SC 2026) does the
   opposite, adopting PGAS/symmetric memory as a core design principle and citing the
   SHMEM lineage — and then reports that **MSCCL++'s multicast variant hung on GB200** and
   had to be excluded from comparison. Two papers one venue-cycle apart reach opposite
   conclusions about the same mechanism. That is a live disagreement, not a succession.

3. **Control placement is a property of the fabric, not of the calendar.** GICC (HPDC 2026)
   is the clearest evidence: the *same runtime* is device-resident on mlx5 InfiniBand
   (kernels build work-queue elements and ring the User Access Region doorbell) and only
   device-*triggered* on HPE Slingshot's CXI provider (the host pre-stages bounded
   operations in a 256-entry Deferred Work Queue against a 2047-counter budget; the GPU
   merely rings a doorbell). GICC coins the distinction "GPU-triggered rather than
   GPU-initiated" for exactly this reason. MSCCL++ independently reports the same
   constraint from the other side — "Current hardware interconnects require a CPU thread
   to initiate the data transfer" — and does not support GPU-initiated RDMA at all, while
   being fully device-resident for intra-node MemoryChannel/SwitchChannel. A single paper
   therefore occupies two "stages" at once, depending on which link is crossed.

4. **The most recent large-scale collectives paper does not cite the device-initiated line
   at all.** *The Big Send-off* (IPDPS 2026) has **no comparison with MSCCL, no comparison
   with GPU-initiated/NVSHMEM approaches, and no discussion of kernel-resident collective
   implementations or device-side algorithm selection**. Likewise PICO (ISC 2026), the
   field's most capable collective-benchmarking framework, supports **only MPI, NCCL and
   RCCL** — it has no SHMEM/NVSHMEM backend and therefore cannot measure a device-initiated
   path at all. A progression narrative requires the later work to cite and build on the
   earlier stage; here the 2026 host-driven work largely does not engage it.

**What the citations *do* support**, stated narrowly:
- A genuine split between **scale-up** and **scale-out** regimes. Inside an NVLink domain,
  device-resident control is routine and the remaining costs are microseconds of
  synchronization (*Every Microsecond Matters* derives `L_SoL = 2·L_L2_RTT +
  L_remote_store` = 1.404 µs on two GB200 and measures barriers at >1 µs, ~40% of a 5 µs
  small-message AllReduce). Across a scale-out fabric, host or hardware mediation persists
  and the remaining costs are bandwidth and algorithm selection.
- A real, independently corroborated finding that **vendor defaults are not the best
  choice**: measured by the SC 2024 interconnect study (MPI beats NCCL by up to an order of
  magnitude on small inter-node transfers; RCCL below half of GPU-aware MPI on a specific
  MI250X GCD pair), by PICO (defaults typically 30–40% off optimal, worst case 1/5 of
  optimal, on Leonardo/LUMI/MareNostrum 5), and by PCCL (NCCL/RCCL offer only ring for
  all-gather/reduce-scatter, giving latency linear in endpoint count).
- A real convergence on **in-fabric reduction** as distinct from device-initiation:
  MSCCL++ SwitchChannel (`multimem.red.release.sys.add.u64`, read in the artifact at
  `include/mscclpp/semaphore_device.hpp:174`), *Every Microsecond Matters* NVLS
  (`multimem.ld_reduce`), and three ISCA/HPCA 2026 in-switch-computing papers. This is the
  branch with the strongest cross-venue agreement in the cluster — and it is orthogonal to
  who initiates.

**Recommended framing for downstream synthesis**: replace the linear progression with a
two-axis map — *who initiates* (host-driven / device-triggered / device-resident) × *which
fabric is crossed* (intra-node peer-mapped / intra-node switch / scale-out RDMA) — and
record that the fabric axis, not the year, predicts the initiation axis.
