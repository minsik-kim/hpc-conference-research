## Reading notes that govern every row

1. **Stable-ID band.** Every ID minted by this cluster is drawn from `GPU-<VENUE><YY>-81..99`, per `governance/ID_NAMING_RULES.md` (IDs are never reused or renumbered). Lower bands in these venue-years were assigned by other clusters.
2. **`prior_corpus_check`.** A repo-wide grep (exact title, normalized title, DOI, arXiv ID, first author + distinctive term) found **no existing corpus analysis** for any assigned paper. Hits were confined to `domains/gpu_systems/census/*.md` (this project's own STEP A/B rows), `census/_evidence/` program dumps, raw TOC dumps under `domains/hpc_quantum/corpus/quantum-hpc-survey/working-evidence/` (existence evidence only), and unrelated word matches in `domains/hpc_systems_operations/`. Rows are therefore `NO_EXISTING_ANALYSIS` **except** where the paper plausibly belongs to the `EXTERNAL_IMPORT_PENDING` ~80-paper AI/HPC corpus under `domains/ai_hpc_systems/`, in which case `KNOWN_EXTERNAL_CORPUS_NOT_IMPORTED` is recorded and **no claim of non-duplication is made**. That applies in particular to the LLM-offload and DLRM/gradient-compression rows.
3. **Publisher access.** `dl.acm.org` → 403, `ieeexplore.ieee.org` → 418 from this environment. Several papers the census marks as open at the publisher are nonetheless `CLOSED_ACCESS` *as determined here*. That is an access-path limitation, not a statement about licence.
4. **Strict counterfactual for this cluster.** A compression algorithm that merely has a CUDA port is `RELATED_GPU` at best. A `NO` must name the GPU-specific property the design depends on — warp ballot/prefix for variable-length encoding, avoidance of inter-block synchronization, working-set residency in shared memory/LDS, coalescing and HBM burst granularity, register-pressure/occupancy trade-offs, being HBM-bandwidth-bound rather than entropy-coder-bound, device-side allocation, or the GPUDirect/`cuFile` path.
5. **Throughput bound.** Every compression row records **what the achieved throughput is bounded by and whether the paper establishes it**. Several papers report only relative throughput against a baseline and never an absolute bandwidth utilisation, occupancy or roofline — those are recorded as `NOT_ESTABLISHED`.
6. **Numbers carry qualifiers.** A compression ratio or throughput without its **dataset, error bound and GPU SKU** is not recorded as a fact.

## D. Cross-paper findings

**1. Variable-length output placement, not compression, is what limits GPU compressors — and every paper solves it differently.**
This is the cluster's central technical finding and it is supported by four independent sources.
- `GPU-ASPLOS25-81` names the standard technique explicitly: "We use **Merrill and Garland's variable look-back strategy** to quickly communicate the write position to the next thread block" `[paper]`, implemented as `propagate_carry` (`speed-compressor-single.cu:111-145`) `[code]`.
- **cuSZp2 implements exactly that**, readable at `[code]` as `flag[warp]` with status values 1/2 separated by `__threadfence()` and a `flag[lookback]` scan loop (`src/cuSZp_kernels_f32.cu:186-239` @ `16e164762f`).
- `GPU-ICS25-81` (Aatrox) **measures its cost**: global prefix-sum **32.8%** of compression time and **39.8%** of decompression time, with block concatenation another **41.5%** attributed to "non-coalesced memory access patterns" from "irregular lengths of compressed data blocks" `[paper]`. About **74% of compression time is placing bytes, not compressing them.**
- `GPU-ICS26-81` (GPZ) **removes it from the critical path** by un-fusing compaction into three kernels — write / device-level prefix-sum / copy — explicitly to avoid the `__threadfence()`-based scheme, and reaches **809 GB/s against a 1008 GB/s peak (~80%)** in that stage `[paper]`.
- `GPU-ISCA25-81` (Ecco) shows what the same problem costs **in silicon**: 64 parallel decoders, **8 speculative sub-decoders each** trying all bit-offsets 0–7, and a **6-stage merge tree** — 5.11 mm² and 7.36 W to make variable-length decoding keep up with an L2.
The four are the same problem at four points on a cost curve: pay a stall (cuSZp2/Aatrox), pay HBM traffic (GPZ), pay area (Ecco), or name it and use the textbook algorithm (ASPLOS 2025).

**2. Almost no paper establishes what bounds its own throughput.**
Of the compression papers read at full text, exactly **one** reports an achieved-vs-peak bandwidth figure (GPZ, and only for one stage), and **one** establishes a bound by stage decomposition (Aatrox). cuSZ-i reports only ratios against cuSZ. The ASPLOS 2025 paper's `SPspeed` is inferably at ~88% of the RTX 4090's HBM peak, but the paper never says so. **Rooflines, occupancy figures and achieved-bandwidth measurements are essentially absent from this literature**, which makes cross-paper throughput claims unusually hard to adjudicate. Two anomalies went unexplained by their own authors: GPZ's compression barely moves from RTX 4090 to H100 (598 → 616 GB/s) while decompression rises 651 → 1091 GB/s — so H100 compression is *not* bandwidth-bound and nothing says what it is bound by.

**3. The SZ family tree, verified from the papers' own citations.**
Reconstructed only from what was read `[paper]` `[README]`:
```
CPU:   SZ2 -> SZ3 -> QoZ  (interpolation; "state-of-the-art CPU-SZ variant in rate-distortion" per cuSZ-i)
                       \
GPU ratio branch:       cuSZ (Tian '20,'21; "GPU version of SZ2", Lorenzo + Huffman)
                          |-- cuSZ+ hi-ratio (Tian '21, RLE)
                          |-- cuSZ-i (Liu, Tian, Wu '24)  = QoZ-style interpolation on GPU + Bitcomp
                          \-- PRISM (PPoPP'26, unread) = multi-level interpolation + progressive retrieval
GPU speed branch:       cuSZx (Yu et al.) ; FZ-GPU (Zhang, Tian '23; "inspired by cuSZ", bit shuffle for Huffman)
                        cuSZp (SC'23) -> cuSZp2 (SC'24) -> cuSZp3 (SC'25, "versatile") 
                                                       \-> AaTrox mode (ICS'25 Aatrox)
                        GPZ (ICS'26) = particle branch, un-fuses the kernel
                        TZ (HPDC'26, unread) = structured-grid sibling of GPZ, same FSU/ANL group
transform branch:       cuZFP (Lindstrom, fixed-rate) ; MGARD-X / MGARD-GPU -> BlockMGARD (SC'26, unread)
lossless branch:        GFC, MPC, ndzip-gpu, nvCOMP -> ASPLOS'25 SP/DP speed/ratio  (NO contact with SZ)
```
**The 2025–2026 compressors cite and beat their own branch, and largely ignore the other one.** Aatrox's baselines are FZ-GPU/cuSZp/cuSZp2/cuZFP — **cuSZ-i is cited in related work but not evaluated against**. GPZ does evaluate against both branches (cuSZp2, PFPL, FZ-GPU, cuSZ, cuSZ-i) and reports that **cuSZ-i lacks 1D data support** and **cuSZp2 produces verification errors on H100** — the only head-to-head robustness evidence found. The single title that promises to collapse the split is **FSZ (SC 2026), "Breaking the Prediction-Throughput Trade-off in GPU Lossy Compression"**, first author **Jiajun Huang** — who also co-authors cuSZ-i, GPZ *and* the gZCCL/ghZCCL collective line. Existence verified via the official SC26 Best Paper finalists announcement.

**4. The compression-in-the-collective line is a separate community from the standalone-compressor line — verified in both directions.**
- **Standalone → collective: no citations.** Targeted checks of cuSZ-i, Aatrox and GPZ found **no reference to gZCCL, hZCCL, ghZCCL or any NCCL-integrated compressor** `[paper]` in any of the three.
- **Collective → standalone: no citations either.** `GPU-SC26-22` (NCCLZ) cites gZCCL, ghZCCL, COCCL and MVAPICH2-class MPI compression, and **no standalone GPU compressor**.
- **Authors overlap heavily** — Sheng Di, Franck Cappello, Jiajun Huang and Xiaodong Yu appear on both sides — so this is not two disjoint groups of people, it is two disjoint citation practices. Recorded as an observation about the literature, with no claim about intent.
- Counting `GPU-ISCA25-81` (hardware cache compression: cites BDI, Buddy Compression, GIST, JPEG-ACT and the LLM-quantization literature, **no SZ-family work**) and `GPU-ASPLOS25-81` (lossless FP: **cites none of cuSZ/cuSZp/cuSZp2/FZ-GPU/cuZFP**), this cluster contains **four mutually non-citing communities working on the same GPU problem**.

**5. Every high-ratio GPU compressor converges on the same architectural move: keep the multi-stage pipeline in on-chip memory and touch HBM once in, once out.**
cuSZ-i resolves its entire stride-4/2/1 level chain inside `__shared__ T data[9][9][33]` `[code]`. The ASPLOS 2025 lossless compressor "keep[s] all chunk data in shared memory between transformations to minimize accesses to the relatively slow main memory" `[paper]`, with a 16 KB chunk sized for exactly that. Aatrox keeps its thread and iteration layers in registers and uses `__shfl_up_sync` "avoiding expensive shared memory" `[paper]`. GPZ under-allocates shared memory deliberately "to enlarge the effective L1 cache" `[paper]`. BlockMGARD's headline contribution (abstract only) is "an **In-cache Block decomposition leveraging GPU on-chip memory**". Five independent groups, one principle. The corollary is that **block/chunk size in this literature is set by the scratchpad budget, not by the algorithm** — 8×8×8 (cuSZ-i), 16 KB (ASPLOS'25), 32×32×32 (Aatrox), runtime-sized (GPZ).

**6. The GPU–storage path splits three ways, and AGILE is the strongest device-resident-control paper in the corpus.**
`GPU-SC25-81` (AGILE): GPU thread writes an NVMe SQE and rings the doorbell; a GPU daemon kernel reaps the CQ — **the CPU is in neither the control nor the data path**. `Phoenix` (SC 2025, artifact-only): refactors the host-driven GDS stack to remove the bounce buffer. `OS2G` (ASPLOS 2025, unread): routes through a DPU. Note the contrast with `_LEDGER_multi_gpu_communication.md`, where `GPU-ASPLOS26-01` records that GPU-initiated **RDMA** is not supported and inter-node transfers need a host proxy: the storage path is easier because NVMe doorbells are plain MMIO registers mappable into the GPU's address space, whereas RDMA needs a driver-mediated work-queue protocol. `[inference]`, from the two papers side by side.
